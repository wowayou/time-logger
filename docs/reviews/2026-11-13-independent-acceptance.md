## 需处理的发现

### F1 · 320px 换行后，扩展热区侵入正文并命中相邻区间（新增回归 + 残余缺口）

**位置**：`styles.css:1417`、`styles.css:1460–1469`，关联 `src/ui.js` 的待核行。

复现：320×820，开启长段待核，合成记录为 08:00–12:00「吃饭」，后接 12:00「下午工作」。该行同时出现「确认 08:00-12:00」和「补一下」，后者换行。

1. 在 `.e-what` 正文盒子内点击 `(160.125, 556.547)`：候选版命中 `confirm-segment`，**没有打开编辑，直接落库 `longConfirm: {startTs: '2026-06-29T08:00', endTs: '2026-06-29T12:00'}`**。Chromium/WebKit 均复现。相同合成数据、相同位置的 Chromium HEAD 对照命中 `start-edit`，打开编辑且 raw 不变，确认这是新增回归，不只是假想的命中重叠。
2. 点击「补一下」中心下方 21px（在其所声明的 44px 目标内）：实际打开的是相邻 **00:00–08:00** 未记录段，而不是当前 **08:00–12:00**。双引擎均复现；原版本也有这个底部缺口，本轮没有补齐。

原因：`min-height:44px` 只留给**整个** `.e-meta`，不能保证 flex 换行后的每一行都有 44px；伪元素仍向上下扩展，侵入正文或落到下一记录。原新增哨兵只测 390px 单行/单按钮，未覆盖 320px 双动作换行。

**建议**：为每个实际操作目标/换行行保留独立布局空间，保持正文与邻行的动作边界；补正文真实点击不写入、换行后 44px 命中和相邻区间哨兵，不用继续改测试点击位置掩盖问题。

证据：`boundary-confirmed-results/` 的 `observation.json`、`pending-controls.png`、`lower-edge-result.png`；`text-click-candidate-results/` 双引擎真实点击均失败，`text-click-baseline-results/` Chromium 对照通过。

### F2 · 存储读取拒绝仍被当成空数据，误报删除并取消撤销（旧缺口未补齐）

**位置**：`src/storage.js:918–927`、`src/sheet_controller.js:1857–1859`、`src/app.js:742–745`。

在表单打开/删除成功后，让隔离上下文的 `window.localStorage` getter 抛出 `SecurityError`，模拟浏览器拒绝站点存储访问，而不只是拒绝 `setItem`：

- 编辑保存显示 **「这条记录已经不存在。」**，不是权限错误。草稿和原始存储确实保留，但用户被错误地告知记录已删除。
- 撤销显示 **「数据已在别处更新，撤销已取消」**，撤销按钮立即隐藏；马上恢复访问权限也无法在原 8 秒窗口里重试。没有其它标签页改数据，删除后的 raw 未变。

双引擎均复现。HEAD Chromium 对照也复现，属于本轮 R03 未覆盖的旧路径，不冒认新增回归。

原因：`loadSnapshot()` 吞读取异常并返回空 entries；源记录检查/撤销版本比较在到达新的严格 `saveChecked()` 之前就退出。现有直接调用 checked writer 的读取拒绝测试不能覆盖这些 UI 前置分支。

**建议**：关键写路径的快照读取应能明确区分「读失败」与「合法空库」；先报告权限错误，再做源记录/版本比较，撤销保留原窗口但不得延时。补 getter/getItem 拒绝的编辑、补录、删除/撤销等真实 UI 路径。

证据：`boundary-confirmed-results/` 两种 `a-denied-site-storage-getter` 观察文件；`baseline-control-results/` 对照。

### F3 · 初始 Shift+Tab 逃出编辑对话框（旧缺口未补齐）

**位置**：`src/sheet_controller.js:626–643`。

键盘聚焦记录 → Enter 打开编辑 → 确认面板本身取得焦点 → **第一个键就按 Shift+Tab**。焦点落到遮罩背后的 `#add-btn`（「记一条」），不是对话框末尾的「删除这条记录」。双引擎均复现，HEAD Chromium 对照也存在。

原因：focus trap（焦点约束，防止键盘焦点跑到模态外）只处理「第一个控件反向走」与「最后一个控件正向走」，没有处理初始焦点仍在面板上的反向导航。新增用例先按 Tab 进入取消键再反向，绕过了这个起点。

**建议**：面板初始焦点的反向导航也须落到最后一个可用控件；保留正常首个 Tab 进入取消键的行为，并增加初始正/反向两条断言。

证据：`boundary-confirmed-results/` 的 `initial-Shift+Tab` 观察文件显示 `inside:false, activeId:'add-btn'`；HEAD 对照同样失败。
