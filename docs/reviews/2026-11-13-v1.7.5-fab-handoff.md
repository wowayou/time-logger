## 范围与结论

用户反馈右下角「记一条」到记录面板的过渡不自然。**局部实现与隔离环境下的完整验收已完成，当前仍是未正式发布的源码候选，线上为 v1.7.4。** 提交推送状态以 [STATUS](../../STATUS.md) 为准；本页不提前声称已部署。

- 原按钮没有真正退场：窄屏只是被面板覆盖，宽屏仍留在遮罩后。
- `styles.css` 复用既有 `body.sheet-open` 与 180ms opacity 过渡，让 FAB 和底部渐隐层打开时淡出、关闭时淡回，打开期间按钮不可命中；减少动效时直接切换。
- 不增加位移、变形、等待或计时器，不改表单/记录 JS、事务、面板动画、焦点或业务 hidden/启动快照。版本六锚点统一到 1.7.5；v1.6.0 的历史行逐字归档，规范仍留最近八版。
- 新增 `tests/v1_7_5_fab_handoff.spec.js`，双引擎 20 项覆盖真实 CSS 过渡中点、关闭恢复、亮暗窄宽、减少动效/键盘、读取拒绝、快速重开、非日视图与表单内刷新。另给历史启动失败的标签套件接入已有被动 `startup_fixture`，只补取证，不改变应用或测试断言。

## 网络调查的证据与边界

两分钟固定诊断中，宿主网络的默认启动与临时进程代理隔离各 60 次启动都就绪（单样本观察上限 5 秒，仅诊断、不计门禁）。只读监听同时记录了宿主一个接口的地址/路由撤销恢复，间隔约 41–42 秒，解析器/hosts 文件未变化。一次额外反证让最小模块页与真实应用的在途请求跨越下一次自然地址事件，两者仍成功。

因此：**接口重配是观察事实，但与之前 ERR_NETWORK_CHANGED 的因果未被证明；代理隔离不是已验证修复。** 不把宿主全量失败倒推为同一个原因，也不把隔离环境的一轮全绿当作历史异常已解决。

## 临时网络隔离与在线能力

用户明确要求继续在隔离网络复验。使用无 sudo 的 `unshare --user --map-root-user --net` 创建进程私有用户/网络命名空间，不改宿主接口、代理、服务或系统策略。通过 Netlink 确认与宿主网络分离；首次工具检查误用了继承的 `/sys` 视图而误判接口数量，随后改用实际命名空间的 Netlink 结果，未把工具误判算作应用故障。

首轮只启用私有回环接口：页面能访问测试 server，但两种浏览器的**原生 `navigator.onLine` 都为 false**。应用的 `checkForUpdate` 与 `repairUpdateChannel` 正确走离线保护，造成八项要求在线的原用例失败。这不是按钮 CSS 回归，也不能通过跳过用例或伪造在线 getter 来掩盖。

修正环境是在另一份私有命名空间中增加一对虚拟以太接口及内部路由；所有接口都在该命名空间里，没有连接宿主或外部 uplink。浏览器原生在线状态实测为 true，原有 `context.setOffline(true/false)` 仍能真实切到 false/恢复 true；没有覆盖 `navigator.onLine`。这恢复了原门禁要求的网络能力，而非削弱应用的离线边界。在线/离线专项通过后才执行上述最终全量。

最终运行前后均核对只有私有回环及虚拟接口，源文件哈希不变。更正环境后只跑一次完整门禁；不再循环执行。
