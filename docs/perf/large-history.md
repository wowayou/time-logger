# v1.6.2 大历史数据验证

2026-11-10，v1.6.2 发布前本地测量；正式发布状态只看 [STATUS](../../STATUS.md)。数据全部合成，不使用个人记录。

## 容量口径

“100 年”适合作为极限正确性和容量不足时的数据保护测试，不是当前产品的存储容量承诺。1926-01-01 至 2026-01-01 共 36,525 个自然日：

| 每天记录数 | 总条数 | 本次样本的 UTF-8 JSON 大小 |
| --- | ---: | ---: |
| 5 | 182,625 | 22,717,050 字节，约 21.7 MiB |
| 15 | 547,875 | 68,516,350 字节，约 65.3 MiB |

条目包含 id、本地时间、中文说明和一个标签；文字越长，文件越大。上述文件字节数不等于各浏览器的 localStorage 配额计量方式。两个引擎对这两组数据调用真实 `saveChecked` 均返回 `quota`，原数据逐字节保留；内存中统计末日均为 1,440 分钟。该容量实验使用本轮中间版本，存储模块未改；不引用中间版本耗时作为最终性能结果。最终逻辑 smoke 另固定覆盖百年 182,625 条的末日统计与不修改源数据，浏览器回归覆盖已有 20,000 条时写入容量异常保留原数据和编辑草稿。

当前仍为 localStorage 全量 JSON 存储。若要保证几十万条可日常录入，需要另评估 IndexedDB（浏览器本地数据库）及迁移、备份、故障恢复，本轮没有扩大存储架构。实际可用年限取决于记录频率、文字长度、浏览器和其它本机存储占用。

## 最终代码的性能对照

运行 `node docs/perf/large-history-measure.mjs b4f78bb /tmp/time-large-history.json`。脚本固定两个浏览器引擎、5,000/20,000 条、每组旧新交替三对，总计 24 个临时上下文；只访问回环地址，不新增依赖、CI 任务或收费服务。每步超时 30 秒，本次外层另设 180 秒截止。报告留在 `/tmp`，不提交生成的时间线文本。

对照基线是任务开始时 `main=origin/main=b4f78bb` 的 `app.js`、`stats.js`、`entry_model.js`，其它文件共用候选版本；两侧都拦截这三个模块，以保持缓存条件相同。固定上海时区、中文、390×820 视口、2026-11-09 12:34 时钟。合成历史大致每天 15 条，首用日已存在。SW（Service Worker，提供离线缓存的浏览器后台脚本）关闭；首次无启动快照，再次加载则采用应用快照。全部 24 次的日/周/月/年可见统计与时间线文本一致，无页面脚本错误。

下表为三次中位数，单位毫秒，**基线 → 候选**：

2 万条下首次启动减少约 19%–20%，日视图减少约 38%–57%，打开表单减少约 47%–53%。已有快照的再次启动没有稳定改善；5 千条的年视图也没有改善。全历史 JSON 解析次数由每次启动 4 次降为 3 次。表格保留所有方向的变化，不承诺任意设备固定耗时。

`app-ready` 来自已有启动诊断标记；交互耗时为同步点击到强制布局结束，不包含随后绘制、动画或网络延迟。这里没有浏览器性能追踪文件，也没有采集 Core Web Vitals（核心网页体验指标）或手机真机数据；这些数字不能当作线上加载、滚动流畅度或真实用户录入耗时。

## 修改与正确性边界

- 统计保留完整的有序记录数组，只对所看范围的起点和紧邻前一条计算区间边界。真实右邻仍用于结束时间、跨日上限、进行中状态与长段确认；不把右邻裁掉。
- 非标准旧时间文本仍走原全扫描，避免把字符串顺序误当成时间顺序。日计划和续记默认起点先筛日期再排序；记录日数只排序去重后的日期。
- 已存在首用诊断日期时，启动不再为它额外解析全历史。`load()` 的新对象图、写前冲突校验和存储格式保持原语义，不增加跨帧可变记录缓存。
- 20,000 条逆序历史的日视图只计算 16 次边界，显示 16 个片段／24 小时；独立注入计数的旧新模块对照为 20,000 → 16 次，因此恢复旧扫描会触发新增次数护栏；保存单条修改时其它记录保持一致。半开区间、前邻、范围外真实右邻、600 分钟完整段的确认标记都有逻辑回归。
- 上海／纽约／柏林逻辑 smoke 均通过；与原统计模块的固定种子随机范围对照各 1,000 次一致，另核对旧时间文本。全量界面测试结果和仍未定位的偶发输入问题统一在 STATUS 登记。
